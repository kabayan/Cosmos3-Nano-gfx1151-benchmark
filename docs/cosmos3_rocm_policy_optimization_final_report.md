# NVIDIA Cosmos3-Nano Policy Model ROCm 最適化最終結果報告書

本ドキュメントは、AMD GPU（Radeon 8060S / gfx1151）および ROCm 7.2 環境における `nvidia/Cosmos3-Nano` Policy Model 推論（30 steps、640x480解像度、17フレーム、バッチサイズ 1）の同期実行時間に対する、最終的な高速化成果および最適化内訳をまとめたものです。

---

## 1. 最終高速化結果のサマリー

すべての同期処理を最適化し、PyTorch TunableOp による GEMM チューニング等を適用した結果、生成時間（サンプリング + VAE デコード）を初期状態から **47 倍高速化**しました。ただし**「対記事比 1.5 倍以内（31.5 秒以下）」の目標には未達**です（1.98 倍）。

> [!CAUTION]
> **2026-07-26 訂正**: 本報告書は当初、基準値を「論文値 29.00 秒」（＝サンプリング 21.00 秒 + デコード 8.00 秒）とし
> 「1.5 倍以内（43.5 秒以下）の目標を完全に達成」と記載していました。しかし調査の結果、**29.00 秒には一次出典が無く**、
> 一次情報は参照記事の「モデル常駐後 **21 秒**で出力」（総所要時間、内訳非公開）のみであることが判明しました。
> 21 秒をサンプリング単体と解釈し出所不明のデコード 8.00 秒を加算したことで基準が 38% 緩み、
> 目標ラインも 31.5 秒から 43.5 秒に緩んでいました。基準値を記事の 21 秒に是正し、達成状況を訂正します。
> 詳細は `.claude/.dls/raw/20260726_doc_baseline_and_conditioning_audit.md`（DLS-006）を参照。

## 2. 実施した主要な最適化施策

### ① モンキーパッチによる Graph Break (ホスト・デバイス同期) の全解消
*   **課題**: トランスフォーマーの各アテンション層の内部（`factored_from_joint_sequence` 内）で呼び出されていた `.tolist()` チェックが CPU-GPU 同期を引き起こし、グラフが細切れに切断されてコンパイル効率が著しく低下していました。
*   **対策**: アサーションロジックをバイパスし、配列演算をテンソル内で閉じるモンキーパッチを [run_cosmos_framework_policy_rocm.py](file:///home/kabayan/workspace/cosmos3/scripts/run_cosmos_framework_policy_rocm.py) に実装しました。
*   **効果**: グラフ全体の統一的な `torch.compile` が可能となり、1ステップあたりの実行時間が 1.99s/it ➔ 1.15s/it まで大幅に高速化されました。

### ② サンプリングループ内の微細な CPU-GPU 同期の排除
*   **課題**: 30ステップのサンプリングループの内部（`_get_velocity`）において、毎ステップで条件マスクが 0 超かどうかを評価する `noisy_mask.sum() > 0` が実行され、都度 CPU-GPU 同期が発生していました。
*   **対策**: 条件分岐を完全に排除し、常にテンソル演算として `pred * noisy_mask` を実行する最適化パッチ（`patched_get_velocity`）を適用しました。
*   **効果**: ループ内の同期が 0 回となり、CUDA Graphs (HIP Graphs) による一気通貫のキャプチャが可能な構造へと平坦化されました。

### ③ CUDA Graphs (HIP Graphs) の有効化
*   **対策**: 同期が排除された状態で `cpp_wrapper = False` および `triton.cudagraphs = True` を指定し、Inductor が生成する Python 実行パスで CUDA Graphs を有効化しました。
*   **効果**: 第1ステップで発生していた再コンパイル遅延（cache miss）が解消し、CPU-GPU 間のコマンド送信オーバーヘッドが極小化されました。ステップ平均速度が **1.145s/it ➔ 1.127s/it** へとさらに短縮されました。

### ④ PyTorch TunableOp による GEMM カーネルの最適化
*   **対策**: `PYTORCH_TUNABLEOP_TUNING=1` を用いて、Policy Model 実行時に使われる動的な行列乗算（GEMM）形状をスキャンし、AMD GPU（gfx1151）で最も実行速度の速い Tensile/hipBLASLt のカスタムカーネルを自動選択させました。
*   **効果**: チューニングテーブル（`tunableop_results00.csv`）が更新され、デフォルト実装よりも高速な演算器が最適に配備されました。

## 3. 結論と今後の展開
本最適化により、NVIDIA Cosmos3-Nano Policy Model を AMD ROCm 環境下で稼働させるにあたり、生成時間を初期状態の約 1965 秒から **41.66 秒**（47 倍高速化）まで短縮しました。一方で**対記事比 1.5 倍以内（31.5 秒以下）の目標には未達**です（1.98 倍）。当初「達成」としていたのは基準値の誤り（29.00 秒には一次出典が無い）によるもので、2026-07-26 に訂正しました（§1 CAUTION 参照）。

実運用のエンドツーエンド遅延で支配的だった**入力観測エンコード（conditioning）**は、2026-07-27 に **81.57 秒 → 0.28 秒**（291 倍）へ削減しました（DLS-008 / DLS-009）。推論結果に到達しない 16 フレーム分をエンコードしていたことを実測で特定したもので、削減は近似ではなく厳密です（サンプリング入力がビット完全一致）。これにより同期総和は **124.91 秒 → 42.44 秒** となり、conditioning はもはやボトルネックではありません。

残る速度差の主因はサンプリング（`generate_samples` 33.84 秒、30 steps）に戻りました。ここはメモリ帯域律速との再評価（`docs/cosmos3_rocm_performance_limit_reassessment.md`）があり、計算内容を変えない範囲での残余余地は小さいと見られます。近似キャッシュ（TeaCache）や INT8 量子化は計算内容を変えるため、対記事同一条件比較の本線からは除外しています（DLS-003）。

さらなる実用的な速度向上を目指す場合は、当初の制約を緩和した以下の施策が考えられます：
1.  **非同期ビデオデコードによる制御遅延の極小化**:
    ロボットの制御側に対してアクションテンソル（アクションのみであれば数ミリ秒でデコード完了）をサンプリング終了（約33.8秒）の直後に即時返却し、最も重い VAE ビデオデコード（7.5秒）は別スレッドで非同期に処理する（アクション応答時間：**実質33.8秒**）。
2.  **生成解像度やサンプリングステップ数の調整**:
    サンプリングステップ数を 20 steps に減らす、あるいは生成解像度を下げることで、クオリティとトレードオフにしつつ実行時間を 20秒台前半まで短縮する。
