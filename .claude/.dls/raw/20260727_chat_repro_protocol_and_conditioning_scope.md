## 構造的な発見: 「再現手順が repo に無い」問題は 1 回では終わらなかった

DLS-005 は Policy について「`--policy-condition-cache` が再現に必須」と記録した。
本セッションは同じ型の問題が **別経路でもう一度**現れることを示した。

| 経路 | 再現に必要だが記録されていなかった要素 | 欠落時の症状 |
|---|---|---|
| Policy（cosmos_framework） | `--policy-condition-cache`（DLS-005） | 322.21 秒（7.7 倍遅く見える） |
| diffusers（T2I/T2V/I2V） | variant `aotriton_tuned` の TunableOp 表（DLS-007） | transformer_forward +22〜55% |

**一般化**: ベンチマーク数値は「スクリプト + 引数」だけでは再現しない。
イメージ・依存インストール手順・環境変数一式まで含めて初めて再現条件になる。
本プロジェクトではこれが 3 箇所（runner の `VARIANTS` / `IMAGE` / `DIFFUSERS_INSTALL`、
別スクリプトのフラグ、docs 内の手打ちコマンド）に分散している。

**誤読を助長した具体物**: `summary.json` の `tunableop_config.enabled` は
CLI 引数（`--tunable-max-tuning-duration` 等）のみを反映し、環境変数
`PYTORCH_TUNABLEOP_ENABLED` を反映しない（`configure_tunableop` L591-597）。
記録側も `false` と表示されるため「記録も TunableOp 無しで測った」と読める。
計測メタデータが実際の実行条件を反映していないケース。

### 未着手の改善候補（dormant）

- 記録 run の完全な実行条件（イメージ / インストール / env / フラグ）を
  artifact の summary.json 自身に埋め込む。今回のような誤読を構造的に防げる
- 現状は「docs を grep して手打ちコマンドを探す」しかない（T2I の記録 case は
  runner の `case_command` に存在せず、`docs/cosmos3-rocm-t2i-non-gemm-improvement-plan.md`
  L289-306 の手打ちコマンドが唯一の記録だった）

本セッションでは提案のみで実施しない。DLS 化もしていない（実施判断が未了のため）。

## 反対視点として検討したこと

### 「v2 の +20〜55% は本当に退行ではないのか」

退行仮説を採る根拠もあった: 記録から 6 週間経過、ホストカーネル更新の可能性、
Strix Halo の APU 共有メモリ。

これを採らなかったのは、**乖離の分布が退行仮説と整合しなかった**ため:

- `vae_decode`（MIOpen conv3d）が 3 モードとも記録と一致（−0.5〜−2.2%）
- VAE warmup も T2I で 659.752 → 659.981 秒（−0.0%）
- 乖離は `transformer_forward`（GEMM 主体）にのみ現れた

環境全体の劣化なら conv3d 経路も遅くなるはずで、この形は
「GEMM の調律表が効いていない」場合の予測とだけ一致した。
**症状の分布を見て仮説を絞る**手順が機能した唯一の例。

## conditioning 削減のスコープ判断

### DLS-003（計算省略系を本線から除外）に抵触するか

抵触しないと判断した。DLS-003 が排除したのは TeaCache 等の**近似**キャッシュで、
「同じ計算の数値誤差」ではなく「計算内容の省略」だから比較前提を壊す、という理由だった。

本件で省くエンコードは `noise = cond_mask * x0 + (1 - cond_mask) * pure_noise` の
`cond_mask = 0` により**厳密に 0 倍される**値の計算であり、
出力は不変（latent frame [0] のビット一致を実測）。近似ではない。

ただしこれは「捨てられる計算を捨てる」ことが常に正当化されるという意味ではない。
記事側が同じ無駄を含んでいる可能性があり、**対外比較としては
「実装の最適化度合いが違う」という差を生む**。本セッションでは
headline 41.66 秒に影響しないため（conditioning は測定対象外、DLS-005/006）
比較の土俵は変わらないと整理したが、conditioning 込みの総和 124.91 秒を
対外的に出す場合は注記が要る。

### 実装方針の選択（ユーザー判断 2026-07-27）

| 案 | 内容 | 結果 |
|---|---|---|
| **A** | スクリプト側モンキーパッチ + エンドツーエンド再測定 | **採用** |
| B | フレームワーク本体（temp_src / /tmp/cosmos-framework）を直接改変 | 不採用 |
| C | 実装せず記録のみ | 不採用 |
| D | conditioning を保留し TeaCache（todo #3）へ | 不採用 |

A を採った理由: `run_cosmos_framework_policy_rocm.py` は既に多数のモンキーパッチを
持つ（attention fallback / graph break 解消 / condition cache）ため手法として一貫する。
B は vendored コードの改変が `rsync -a temp_src/ /tmp/cosmos-framework/` や
上流更新で失われる。C は 124.91 秒という対外数値の 65% が無駄と分かった状態で
放置することになる。

## 本セッションの失敗パターン（3 回同型）

| # | 誤り | 原因 | 実測で否定された内容 |
|---|---|---|---|
| 1 | v1 検証 run が記録条件と別物 | イメージ / diffusers を確認せず起動 | T2I が API 不在でクラッシュ |
| 2 | 「+20〜55% の退行」 | variant の env 全体を確認せず | TunableOp 表適用で ±0.6% に |
| 3 | 「189 フレームをエンコード」 | 分岐（action 系の早期 return）を見落とし | 実測 17 フレーム |

共通構造: **実測で分岐・条件が確定する前に結論を出した**。
3 回とも報告直前ないし直後に自力で気づいたが、2 回はユーザーに誤情報を報告した後だった。

対策として本セッション後半で採った手順（有効だった）:
- 手書きしたコマンドを `case_command()` の生成物と文字列比較してから実行
- 静的読解の結論を、テンソル形状のダンプで確認してから報告
- 計測値が想定と桁違いなら、まず計測系（MIOpen 探索）を疑う
