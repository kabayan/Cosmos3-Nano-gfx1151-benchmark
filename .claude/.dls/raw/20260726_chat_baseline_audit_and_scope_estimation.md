## 誤報の二段構造（CC 側の失敗の記録）

1. **一段目**: TeaCache run（warmup なし単発）のコールド 1 回目 969.85s（旧）vs 1867.3s（今日）を比較して
   「約 2 倍の劣化」と報告。カーネルコンパイル等のノイズ区間同士を比べており、プロジェクトの
   測定プロトコル（warmup 2 回 + 測定 run の同期総和）と無関係な数字だった。
2. **二段目**: 本線プロトコルを再実行した際、`--policy-condition-cache` を渡さなかった。
   同フラグは (a) warmup 時の conditioning を測定 run で再利用し、(b) プロファイラ経路を有効化して
   ステージ境界で同期を取る。落とすと測定スコープと同期の取り方の両方がずれ、322.21s という
   比較不能な値が出た。CC はこれを「退行」と解釈した。

教訓: **headline 数値を再現するときは、まず当時の実行フラグ・env を特定してから走らせる。**
本件では再現手順が repo のどこにも記録されていなかったことが根本原因（→ DLS-005 で記録）。

## 中立的再評価（CC の前言撤回）

CC は当初「conditioning 約 82 秒を除外した 41.66 秒を Total と称するのは不当」と判断し、
案B（実測側も conditioning 込み 124.91 秒・5.95 倍に揃える）を推奨した。

その後、記事側スコープを推定する過程で撤回した。根拠:

1. **不等式**: 本環境の conditioning 単体 81.57 秒 > 記事の総時間 21 秒。
   記事の 21 秒が conditioning を含むなら、DGX Spark は全体で 6 倍以上速い必要がある。
2. **他 3 モードによる較正**: T2I 1.23x / T2V 1.46x / I2V 1.47x（記事比）。
   T2I・T2V は重い入力エンコードを持たないため、これらは「サンプリング + デコード」同士の
   比として使える。DGX Spark は本環境比 1.2〜1.5 倍程度でしかない。
3. 6 倍 vs 1.2〜1.5 倍は同一 GPU・同一拡散系ワークロードとして整合しない。

→ **記事の 21 秒も入力エンコードを含まない「生成のみ」と推定**（確度 7〜8 割）。
conditioning 除外自体は apples-to-apples として妥当であり、問題は基準値 29.00 秒の側にあると結論。

## 構造的発見: und_branch_cache と condition_cache は本質が違う

「Policy 以外も同じ値が出るか検証」（ユーザー指示）の過程で、過去 run の成果物から判明した。

| | キャッシュ対象の素の呼ばれ方 | run 跨ぎキャッシュで不当に消える分 |
|---|---|---|
| `und_branch_cache`（T2I / I2V） | 35 ステップで毎回再計算（理解ブランチは全ステップ不変） | 1 回分のみ（約 1.5 秒） |
| `condition_cache`（Policy） | 1 生成につき 1 回のみ | 全部（81.57 秒） |

und キャッシュ統計は `transformer_calls: 70, write_calls: 1, read_calls: 69`。
1 生成 35 ステップ × 2 run で 70 回中 69 回がキャッシュヒット。
本来「1 生成 1 回」が正しい実装であり、34 回分の削減は正当な最適化。
35 回目（初回計算）だけが測定 run で免除されている。

I2V 実測: und キャッシュ無し transformer 71.691s/35 回（2.048 s/回）、
有り 19.68s/35 回（0.562 s/回）→ und ブランチ 1.486 s/回。
正しく「1 生成 1 回」にすると I2V は 25.045 → 約 26.5 秒（対記事 1.47x → 1.56x）。誤差範囲。

T2V は `und_branch_cache: None`（キャッシュ未使用）、測定 run の unattributed も 1.201 秒のみ。
32.165 秒は素の warm 実測でクリーン。

→ **訂正が必要なのは Policy だけ**という判断の裏付けになった。

## 未検証仮説（後で実機・外部確認する価値あり）

1. **記事の 21 秒のスコープ**: 上記推定は間接証拠のみ。記事著者への確認、または
   NVIDIA Cosmos 公式ベンチマークの計測スコープ判明で裏取りできる。
   確度が上がれば DLS-006 の assumption を更新する。
2. **conditioning が 189 フレームをエンコードしている疑い**: `condition_frame_indexes_vision=[0,1]` で
   条件として使うのは 2 フレームのはずだが、decode が 7.35 秒 / 17 フレーム = 0.43 秒/フレームなのに対し
   conditioning 81.57 秒 ÷ 0.43 ≈ 189 フレーム分に相当する。
   `get_data_and_condition` が入力観測動画の全フレームを VAE エンコードしている可能性。
   事実なら**未着手の大きな最適化余地**（測定対象外だったため最適化対象にもなっていなかった）。
3. **コールドスタント挙動の差**: 記録 6/14 は warmup1 で初回サンプリング到達まで 106 秒だったが、
   今日は 726〜733 秒。定常状態は一致するため結論に影響しないが、6 月はコンテナに MIOpen カーネル
   キャッシュが温まっていた可能性。ホスト側に MIOpen キャッシュをマウントすれば実験時間を短縮できる見込み。
