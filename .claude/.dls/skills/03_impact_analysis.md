# Skill 03 — 変更リクエスト影響範囲分析

変更リクエストを受けたとき、depends_on / affects を辿って影響範囲を特定する。
「全部調べます」→「影響範囲はこれ、工数を見積もります」に変換する。

---

## いつ使うか

- クライアント・ユーザーから変更リクエストを受けたとき
- 実装中に仕様変更が必要になったとき
- リファクタリング前の影響調査

---

## 手順

### Step 1: 変更リクエストを整理する

変更内容を以下の観点で整理する（投げる前に自分で確認）:

- 何が変わるのか（what レベルの変更）
- 誰からの要望か（requested_by）
- 既存の仕様との差分はどこか

### Step 2: 影響範囲分析を Claude に投げる

**プロンプトテンプレート:**

```
以下の変更リクエストについて、.claude/.dls/active.md を参照して影響範囲を分析してください。

【変更リクエスト】
（変更内容をここに記載）

【依頼者】
（クライアント名 / ユーザー名）

【分析手順】
1. 変更リクエストに最も関連する既存エントリを特定する
2. 該当エントリの affects を辿り、影響を受けるエントリを全て列挙する
3. 影響エントリの depends_on を確認し、連鎖的な影響がないか確認する
4. 以下の3分類で結果をまとめる:

   A. 実装変更のみ（既存エントリの what に変更なし）
      → コードを修正するだけで完了
   
   B. 仕様矛盾あり（既存エントリの what と両立しない）
      → 関係者への確認が必要。どのエントリと矛盾するかを明示
   
   C. ユーザー間衝突（異なる requested_by のエントリと矛盾する）
      → 関係者間での調整が必要。衝突するエントリと依頼者を明示

5. 分類 A の場合: 修正が必要なファイル・モジュールを列挙する
6. 分類 B/C の場合: 確認・調整が必要な内容を整理する
7. 変更後に新規 DLS エントリが必要な判断を識別する
```

### Step 3: 分類に応じて対応する

**分類 A（実装変更のみ）の場合:**
1. 修正対象のファイルを特定
2. 変更内容を DLS エントリとして追加（`supersedes` で旧エントリを参照）
3. 旧エントリを archive.md に移動
4. 実装を修正

**分類 B（仕様矛盾あり）の場合:**
1. 矛盾内容を整理してクライアントに確認依頼
2. 確認結果を `.claude/.dls/raw/YYYYMMDD_email_confirmation.md` に保存
3. 確認後に分類 A として処理

**分類 C（ユーザー間衝突）の場合:**
1. 衝突内容と関係者を整理
2. 関係者調整の場を設定
3. 調整結果をエントリ化

---

## 影響範囲の報告フォーマット

クライアントへの報告時に使用する:

```
## 変更リクエスト影響分析レポート

**リクエスト内容**: （変更内容の要約）
**分類**: A / B / C

### 影響を受けるエントリ
- DLS-XXX: （内容の要約） → （影響の内容）
- DLS-XXX: （内容の要約） → （影響の内容）

### 対応方針
（分類に応じた対応方針）

### 確認が必要な事項
（あれば）

### 概算工数
（分類 A の場合のみ）
```

---

## 注意事項

- affects / depends_on が不完全な場合がある（本質的な限界）
  → 分析後も「これ以外に影響がないか」を実装担当者が確認する
- requested_by が異なるエントリの衝突は見落としやすい
  → 分類 C を意識的に確認する
