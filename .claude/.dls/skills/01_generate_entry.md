# Skill 01 — DLSエントリ生成

ヒアリングメモ・メール・チャットログ等の生情報から DLS エントリを生成する。

---

## いつ使うか

- ヒアリング後にメモをエントリ化したいとき
- メールや Slack の内容から判断を記録したいとき
- 実装中に発生した判断をエントリ化したいとき

---

## 手順

### Step 1: 原本をrawに保存する

```
`.claude/.dls/raw/YYYYMMDD_種別_概要.md` にコピーして保存する
（既存ファイルは編集しない。新規ファイルとして追加する）
```

### Step 2: 次の指示で Claude に投げる

---

**プロンプトテンプレート:**

```
以下の情報から DLS エントリを生成してください。

【情報ソース】
（ヒアリングメモ / メール本文 / チャットログをここに貼り付ける）

【生成ルール】
1. `.claude/.dls/active.md` を読み込み、次のエントリ番号（現在の最大番号+1）を使う
2. `.claude/.dls/templates/entry.md` のフルテンプレートに従う
3. `what` には Why/What のみ記載し、How（ライブラリ、データ構造、処理順序）は含めない
4. `why.business` にはビジネス上の動機またはユーザーの課題を書く
5. `sources` には `.claude/.dls/raw/YYYYMMDD_種別_概要.md` のパスを記載する
6. 既存エントリと依存・影響関係がある場合は `depends_on` / `affects` を設定する
7. 既存エントリと矛盾する可能性がある場合は明示する
8. 判断として記録すべき粒度かどうか「3日後の自分が理由を理解できるか」で判断する

【原本パス】
.claude/.dls/raw/YYYYMMDD_種別_概要.md
```

---

### Step 3: 生成されたエントリを確認する

確認観点:
- [ ] `what` に How が混入していないか
- [ ] `why.business` がビジネス動機・ユーザー課題を説明しているか
- [ ] `sources` のパスが実在するか
- [ ] `depends_on` / `affects` に漏れはないか
- [ ] 既存エントリと矛盾していないか（Step 4 で確認）

### Step 4: 整合性チェックを実行する

`.claude/.dls/skills/02_consistency_check.md` に従って整合性を確認する。

### Step 5: active.md に追記する

確認が完了したら `.claude/.dls/active.md` の末尾に追記する。
エントリ数カウントを更新する（ファイル冒頭のコメント）。

---

## ヒアリング中のリアルタイム活用

ヒアリング中に以下のパターンを検知したら即座にエントリ候補としてメモする:

| パターン | 記録すべき理由 |
|---|---|
| 「〜にしてほしい」 | 要求の根拠（why.business）を必ず確認 |
| 「〜はやめてほしい」 | rejected_alternatives の候補 |
| 「前回〜だったから」 | depends_on の候補 |
| 「たぶん〜のはず」 | assumption（confidence: medium/low）の候補 |
| 「〜が変わった場合は」 | affects の候補 |

---

## 注意事項

- エントリ数が目安 30 件を超えそうな場合は減衰候補レビューを先行する。Phase 集約期の超過は許容（DLS-144）
- 1つのヒアリングから複数エントリが生成されることは正常
- 「粒度が小さすぎる」と感じた場合でも、why が明確なら記録する価値がある
