# Skill 02 — 整合性チェック

新しい DLS エントリと既存エントリの矛盾・依存関係の漏れを検出する。

---

## いつ使うか

- 新エントリを active.md に追加する前（必須）
- 変更リクエストを受けて既存エントリを更新するとき
- 定期的な棚卸し時（月次など）

---

## 手順

### 次の指示で Claude に投げる

**プロンプトテンプレート:**

```
以下の新しい DLS エントリと、既存の active.md を照合して整合性をチェックしてください。

【新しいエントリ】
（生成されたエントリをここに貼り付ける）

【チェック観点】
1. **矛盾検出**: 新エントリの what/why が既存エントリと矛盾していないか
   - 両立しない要求ペアを特定する
   - 矛盾がある場合は該当エントリ番号と矛盾の内容を明示する

2. **依存関係の漏れ**: depends_on / affects の設定が適切か
   - 新エントリが前提としている判断が depends_on に含まれているか
   - 新エントリの変更で影響を受けるエントリが affects に含まれているか
   - 影響を受ける既存エントリの affects フィールドに新エントリを追記すべきか

3. **supersedes の確認**: 新エントリが既存の判断を覆す場合
   - supersedes に該当エントリ番号が記載されているか
   - 覆されるエントリを archive.md に移動する必要があるか

4. **assumption の監視**: confidence: low の未検証前提
   - 新エントリの assumption は適切な confidence レベルか
   - 既存の confidence: low な assumption と関連していないか

5. **whatのHow混入チェック**: what フィールドに実装手段が含まれていないか
   - ライブラリ名、フレームワーク名が含まれていれば指摘する
   - 内部のデータ構造・アルゴリズムが含まれていれば指摘する
   - 処理の順序・ステップが含まれていれば指摘する

【出力形式】
問題なし / 要確認 / 要修正 のいずれかを先頭に明示し、詳細を続ける。
```

---

## チェック結果の対処

| 結果 | 対処 |
|---|---|
| **問題なし** | active.md に追記して完了 |
| **要確認（矛盾の可能性）** | 関係者に確認してから追記 |
| **要確認（depends_on漏れ）** | フィールドを補完してから追記 |
| **要修正（whatにHow混入）** | what を書き直してから追記 |
| **要修正（supersedes必要）** | supersedes を追記し、古いエントリを archive に移動 |

---

## 既存エントリの affects 更新

新エントリ追加時に既存エントリの `affects` を更新する必要がある場合:

```
【手順】
1. active.md の該当エントリを開く
2. affects フィールドに新エントリ番号を追記する
3. affects フィールドがない場合は追加する

例:
## DLS-003
...
- **affects**: DLS-007（← 今回追記）
```

---

## 定期チェック（月次推奨）

**プロンプトテンプレート:**

```
.claude/.dls/active.md の全エントリを対象に以下を確認してください。

1. confidence: low の assumption を列挙する（放置アラート）
2. affects/depends_on が設定されていないエントリを列挙する（依存関係の漏れ候補）
3. 相互に矛盾している可能性があるエントリペアを列挙する
4. supersedes が記録されているが archive に移動されていないエントリを特定する
5. 減衰候補の検出:
   date が長期間前（目安: 最終コミットから3ヶ月以上）で、他エントリの depends_on/affects
   から参照されていないエントリを列挙する。git log --since="90 days ago" --name-only と
   where を照合し、コードが活発に変更されているか確認する。
   → 活発なら残す。触れられていなければ archive 移動を検討する。
```
