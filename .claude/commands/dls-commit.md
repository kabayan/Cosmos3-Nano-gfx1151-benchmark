# コミット & セッション状態の保存

未コミットの変更をコミットし、`/clear` に備えてセッション状態を `tasks/next.md` に書き出してください。

---

## Phase 1: コミット

### 1. 状態確認

以下を並列で実行:
- `git status`（未追跡・変更ファイルの確認）
- `git diff`（差分の確認）
- `git log --oneline -5`（直近のコミットメッセージのスタイル確認）

### 2. コミット実行

- 変更がなければ「コミット対象の変更はありません」と報告してPhase 2へ進む
- 変更がある場合:
  1. 変更内容を分析し、簡潔なコミットメッセージを作成する
     - **cross-project DLS 番号の注意**: コミットメッセージの `DLS-XXX` は **本プロジェクトの `active.md` に存在する番号のみ**を裸で使う。dls-core から配布された成果物（skill / hook / adapter 等）をコミットする場合、その出自である **dls-core 側の DLS 番号は `dls-core DLS-XXX` と明示**するか、番号を使わず内容で記述する（例: 「Codex continue skill 追加」）。本プロジェクトの番号空間と混同させない
  2. `.env` やクレデンシャル等の機密ファイルが含まれていないか確認する
  3. 関連ファイルを `git add` でステージングする
  4. コミットメッセージの末尾に `Co-Authored-By: Claude <noreply@anthropic.com>` を付ける
  5. コミットを実行する

### 3. コミット後の確認

- `git status` でコミット成功を確認する
- pre-commit hook が失敗した場合は修正して新しいコミットを作成する（--amend しない）

---

## Phase 1.5: DLS 関連性チェック

`.claude/.dls/active.md` にエントリがある場合のみ実行する（0件ならスキップ）。

1. `git diff --name-only HEAD~1 HEAD` でコミット対象ファイルを取得
2. `.claude/.dls/active.md` の各エントリの `where` とベストエフォートで照合する
   （where が抽象的な記述の場合はモジュール名・機能名で判断する）
3. 結果を簡潔に報告:
   - **関連エントリ**: where が重なるエントリ番号と概要（＝強化シグナル）
   - **要検証**: 関連エントリに `confidence: low` の assumption があればフラグ
4. Phase 2 の next.md に関連エントリ番号を含める

---

## Phase 1.6: 議論ノートの抽出（**必須判定**）

⚠️ **重要**: 議論ノートが消失すると **復活できない**。会話コンテキストは `/clear` / cc 再起動で失われるため、議論ノートが唯一の原本となる。

このフェーズは **必ず判定を行い結果を明示する**。スキップする場合も「議論なし」の判断理由を明示する（黙って飛ばさない）。

### 議論モード時の強制実行

`tasks/next.md` の「DLS 議論モード状態」セクションを確認:
- `mode: discuss` または `mode: plan` であれば、抽出判定を **強制実行**（スキップ不可）
- このセッションで `/dls-discuss` または `/dls-plan` が呼ばれていた場合も同様
- 議論モード時は議論ノートの作成と DLS 化（または DLS 草案の active.md への追加）を **必ず提案する**
- 完了後、`tasks/next.md` の議論モード状態セクションを削除（モード解除）

### 判定対象

以下のいずれかに該当する議論があったか判定する:

- 設計探索（minimal slice / YAGNI / 中立的再評価）
- 外部事例参照（他ツール・他プロジェクトとの比較）
- 抽象化レイヤーの議論（3 層モデル / WBS 相関 / 粒度判定など）
- 却下案の理由整理
- 検証はまだだが後で実機検証する価値がある仮説の提示

**疑わしいなら作成側に倒す**（false negative < false positive、軽い議論ノートは後で archive 可能だが消失した議論は復活不能）。

### 手順

`.claude/.dls/skills/07_discussion_notes.md` の **手順** を呼ぶ:

1. cc が今セッションを振り返り、抽出対象の議論があったか判定する
2. **判定結果を必ず明示**:
   - 抽出する: 下記 3 へ進む
   - スキップする: 「議論なし」と判断した理由を **必ず明示**（例: 「本セッションはバグ修正のみで設計議論なし」）
3. 抽出する場合:
   1. ファイル名候補を提案（`YYYYMMDD_chat_<topic>.md`、保存先は `.claude/.dls/raw/`）
   2. ノート本文のドラフトを作成（推奨セクション: 出発点 / 外部事例参照 / 中立的再評価 / 確定事項 / 関連 DLS エントリ / 議論再開時の起点 / 検証根拠）
   3. **ユーザー確認**: ファイル名・本文・関連 DLS エントリへの sources 追記を提示
   4. 承認後、`.claude/.dls/raw/` に保存
   5. 関連 DLS エントリ（`.claude/.dls/active.md`）の `sources` にリンクを追記
   6. コミット対象に含める

### ルール

- **自動保存はしない**: ドラフト → ユーザー承認 → 保存の順で進める
- **スキップ判断は明示**: 「判定対象に該当する議論なし」を必ず言語化
- **判定基準**: 「**3 ヶ月後にこの議論の構造を再構築できるか**」— 再構築困難なら抽出
- **/clear / cc 再起動の前は必須**: 二段防衛（DLS-146）— Stop hook（`dls-stop-reminder.py`）が CC 応答完了ごとに予防警告、SessionEnd hook（`dls-session-end-reminder.py`, matcher: `"clear"`）が /clear 直前に最終確認警告を出す

## Phase 1.7: todo.md 衛生管理（完了タスク整理）

`tasks/todo.md` が存在し、`Active` セクション以外（`Done` / `Review` / `Plan` 等）または
`- [x]` チェック済みの行があれば実行する。すべて Active のみ・空・不在ならスキップする。

`/dls-clean` の **Phase 4（commit 後の todo 整理）** として、`.claude/.dls/skills/06_todo_hygiene.md` の **手順 A** を呼ぶ:

1. 直前のコミット (`HEAD`) の変更ファイル一覧とメッセージ本文を取得する
2. todo.md の完了候補（チェック済み行・Active 外の項目・コミット内容と意味的に対応する項目）を抽出する
3. 各候補の永続化先を確認する:
   - 変更内容 → コミットメッセージ + diff で永続化済みか
   - 判断 → 該当する DLS エントリがあるか
4. **永続化されていない情報があれば**、DLS エントリ作成 / コミット amend / lessons.md 追記のいずれかを促す
5. 永続化済みの候補のみ、ユーザー承認を得てから todo.md から削除する

**自動削除はしない**。提案 → ユーザー確認 → 削除の順で進める。

## Phase 2: セッション状態の保存

以下の情報源を確認し、構造化された引き継ぎ情報を作成してください。

### 確認すべき情報源

1. `tasks/todo.md` — 現在のタスクリストと進捗
2. `.claude/.dls/active.md` — 直近のDLS判断エントリ
3. `git status` / `git diff --stat` — 未コミットの変更
4. `git log --oneline -5` — 直近のコミット
5. 現在のセッションで行った作業内容（会話コンテキストから）

### tasks/next.md のフォーマット

以下の形式で `tasks/next.md` を作成（上書き）してください:

```markdown
# 次のセッションへの引き継ぎ

> 作成日時: YYYY-MM-DD HH:MM
> 前セッションの要約: （1〜2文で）

## 現在の状態

（何がどこまで進んでいるか。具体的なファイル名・行番号を含める）

## 完了済み（今セッション）

- （今セッションで完了した主要な作業をリスト）

## 次のアクション

→ `tasks/todo.md` の `Active` セクションを参照（DLS-123: タスク本体は todo.md に一元化）

## ブロッカー・注意事項

- （あれば。なければ「なし」）

## 関連ファイル

- （作業中のファイルパスをリスト）
```

### ルール

- 会話コンテキストが失われることを前提に、**このファイルと todo.md を読めば再開できる**レベルで書く
- 曖昧な表現を避け、具体的なファイルパスとタスク番号を使う
- 「やりかけ」の状態は特に詳しく記述する（どこまでやって何が残っているか）
- 日時は `date` コマンドで取得する
- **タスク本体は `tasks/todo.md` の `Active` に書く**。next.md の「次のアクション」セクションは
  todo.md への参照リンクのみ（DLS-123）。タスク文言を直接 next.md に書くと DRY 違反
- 今セッションで新規発生した未完了タスクは、Phase 2 完了前に `tasks/todo.md` の `Active` に追記する
